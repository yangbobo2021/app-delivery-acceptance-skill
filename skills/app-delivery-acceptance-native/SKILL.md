# 交付验收

内置记录、执行和看板工具用 Node.js 24.12+ 直接运行。实际测试和覆盖率采集沿用被测项目的工具链。

建 PLAN 前，按本轮指令确定交付物、停止点和明确排除的动作，再按实际依赖选择步骤。续接或重跑可沿用仍适用的项目与需求，执行范围以本轮指令为准。用户调整范围时先更新计划，只继续范围内的工作。必需的前置条件缺失且无法在本轮范围内满足时，说明具体阻塞。用户给出 `AT-…` 时，创建或续接前核对并原样使用。

- 开发完成后验收。确认需求基线，按[场景范围](references/definitions/entry.md#交付场景推导)沿用场景并在授权内补齐缺口。按需求准备、执行和复审下属场景。按用户要的结论选择[场景结果或逐需求交付判定](references/execution/entry.md#按交付范围收尾)。只匹配任务交付缺口后停止。
- 已确认需求的测试驱动开发。读取[测试驱动开发](references/development.md)，先取得可复核的红灯。只交测试时到红灯复审结束，获授权实现时才修改产品并取得同版绿灯与回归证据。
- 维护期盘点。读取[交付盘点](references/inventory.md)，按当前版本核对已有依据与证据。用户授权哪些检查就复跑哪些，盘点报告交付后停止。

需求基线是本次验收采用的已确认需求。测试场景定义要验证的业务行为和验收判据，可随范围核对和复审补充、修订。具体数据、准备动作和操作步骤写在用例。记录快照用于追溯当时采用的需求和场景。

三条路径都以需求组织修改与结论。每条需求关联多个场景，每个场景可包含多个自动用例或人工验证项。验证项身份跨阶段沿用，每次执行新增记录，版本、结果、证据和复审都归入该次记录。同一需求下的场景可统筹实现和回归，按场景分别保存判据及结果。跨需求共用实现时，先列明受影响的需求及修改前的证据，再分别验收。按[截图与落盘核对](references/results/entry.md#截图与落盘核对)留存证据和进度。

在实际业务操作前创建原生 PLAN。每条用「动作 + 业务对象」写一个短句，例如「调试报名与播放权限用例」「验证退出后能否续签播放」。逐条独立阅读也应知道在做哪块功能，「复审 6 个用例」需要补上业务名。让用户在窄栏里两行内读完。每条最多 48 个半角字符的宽度，中文等全角字符按 2 个计。写入前核对长度，超限就缩短业务名或按实际工作拆项。待办、进行中、已完成和最终结论都遵守同一限制。

批次用业务范围和实际数量概括。PLAN 省略完整 ID 清单、UUID、文件路径、收据和命令，精确范围保存在操作请求、复审交接和证据记录。开始匹配、调试、执行或复审前，先更新进行中条目，让它描述即将开展的工作，同时保留下一步。正式执行或人工观察按[执行前更新 PLAN](references/execution/entry.md#执行前更新-plan)操作，启动 Reviewer 按[复审交接顺序](references/execution/reviewer.md)操作。

续接已有 PLAN 时，把现存的长条目也改写成业务短句，并保留真实状态。实际结果落盘后才勾选。阻塞时简述原因并保留依赖项为待办。每条需求在最终 PLAN 保留独立的简短结论。若宿主没有计划工具，说明当前会话的进度展示限制。

- [需求基线与场景](references/definitions/entry.md)负责创建验收、记录需求基线、生成或修订测试场景、核对范围及查询。仅创建、仅记录需求基线或仅查看时，完成对应操作后停止。
- [用例设计](references/case-preparation/design.md)按当前测试场景为每个用例确定 TC ID 和自然语言描述，记录必测检查及设计缺口。只设计时读回设计收据后停止。
- [用例实现](references/case-preparation/implementation.md)按设计的 TC ID [关联已有测试](references/case-preparation/entry.md)，按授权补充代码或人工验证步骤。只匹配时交付实际匹配和缺口后停止。
- [测试与覆盖环境](references/case-preparation/environment.md)负责运行探测和采集探测。只准备环境时以实际就绪或阻塞收据为终点。
- [执行与复审](references/execution/entry.md)负责正式执行、证据、独立复审、历史复核及授权内的返修。只准备用例时在核对设计和实现的独立复审后停止。
- [结果展示](references/results/entry.md)负责读取结果和导出报告。用户只看结果时以已有材料交付。
- [验收生命周期](references/lifecycle/entry.md)负责分析、单独场景评估、手工观察、变更、恢复、归档、整体验收及项目知识。

按实际依赖更新一张原生 PLAN。初次设计复审可进入初始计划，可能的返修、新版调试和重审只在收到真实的需修订意见后追加，即使用户预先允许返修。分别在实际修订并调试、再次复审结束时更新对应状态。让已完成的复审保留真实结论，例如「复审 v1（需修订）」。阻塞和已执行但未通过的情况分别展示。

输出实际验收 ID、已完成工作、产物位置与版本，或具体阻塞原因。按用户确认的来源记录需求基线，并注明测试场景的来源。
