# 交付验收

先根据用户目标和授权选择路径。用户给出 `AT-…` 时，它是本次验收 ID，创建或续接前核对并原样使用。

- 开发完成后验收。按[场景范围](references/definitions/entry.md#交付场景推导)沿用已补齐的场景，或先冻结原始范围再逐需求补齐。按需求准备、执行和复审下属场景。只匹配任务交付缺口后停止。
- 已确认需求的测试驱动开发。读取[测试驱动开发](references/development.md)，先取得可复核的红灯。只交测试时到红灯复审结束，获授权实现时才修改产品并取得同版绿灯与回归证据。
- 维护期盘点。读取[交付盘点](references/inventory.md)，按当前版本核对已有依据与证据。用户授权哪些检查就复跑哪些，盘点报告交付后停止。

三条路径都以需求组织修改与结论。每条需求关联多个场景，每个场景可包含多个自动用例或人工验证项。验证项身份跨阶段沿用，每次执行新增记录，版本、结果、证据和复审都归入该次记录。同一需求下的场景可统筹实现和回归，按场景分别保存判据及结果。跨需求共用实现时，先列明受影响的需求及修改前的证据，再分别验收。按[截图与落盘核对](references/results/entry.md#截图与落盘核对)留存证据和进度。

读所选入口后，在实际业务操作前创建原生 PLAN。第一张计划列出已知的具体需求和场景。核对到用例或人工验证项 ID 后，在操作开始前把对应条目细化到「需求 › 场景 › 验证项 · 动作」。例如「R1 › SC1 › TC-BOUNDARY · 执行并保存结果」和「R1 › SC1 › TC-MANUAL · 核对错误提示」。当前工作标为进行中，同时保留下一步和已知后续范围。每条需求保留独立的结论条目，直到最后一次 PLAN 更新。收到真实结果后才勾选，阻塞时记录原因并保留依赖项为待办。若宿主没有计划工具，说明当前会话的进度展示限制。

开始匹配、调试、执行或复审前，先调用计划工具确认进行中条目对应即将操作的需求、场景、验证项和动作。切换对象或动作时先更新 PLAN，再发起该步调用。正式执行和人工复核按验证项发起，人工重跑用「首次观察」「第二次观察」等区分。设计复审、正式执行和执行复审分别列项。启动任何 Reviewer 前，先定稿完整交接范围，再按[原生 PLAN 更新顺序](references/execution/reviewer.md)把同一段范围同时用于进行中条目与实际交接。

- [依据与定义](references/definitions/entry.md)负责创建、冻结和查询。仅创建、只冻结或仅查看时在该能力返回后停止。
- [用例准备](references/case-preparation/entry.md)负责匹配已有用例。在仅匹配任务中，交付实际匹配和缺口后停止。需要补齐用例时进入[用例生成、调试与设计复审](references/case-preparation/design.md)，按同版结果交接。
- [测试与覆盖环境](references/case-preparation/environment.md)负责运行探测和采集探测。只准备环境时以实际就绪或阻塞收据为终点。
- [执行与复审](references/execution/entry.md)负责正式执行、证据、独立复审、历史复核及授权内的返修。只准备用例时在独立设计复审后停止。
- [结果展示](references/results/entry.md)负责读取结果和导出报告。用户只看结果时以已有材料交付。
- [验收生命周期](references/lifecycle/entry.md)负责分析、单独场景评估、手工观察、变更、恢复、归档、整体验收及项目知识。

按实际依赖更新一张原生 PLAN。初次设计复审可进入初始计划，可能的返修、新版调试和重审只在收到真实的需修订意见后追加，即使用户预先允许返修。分别在实际修订并调试、再次复审结束时更新对应状态。让已完成的复审保留真实结论，例如「复审 v1（需修订）」。阻塞和已执行但未通过的情况分别展示。

输出实际验收 ID、已完成工作、产物位置与版本，或具体阻塞原因。用户项目的定义来源决定冻结内容。
