# 结果展示

用 [结果工具](../../scripts/results.mts) 读取已有证据。查看是只读操作；报告将实际快照及所引用的证据字节放到同一本机导出目录。需要共享时，由用户明确选定可归档的内容。

```sh
node "<结果工具>" --root "<项目>" view "<AT-ID>"
node "<结果工具>" --root "<项目>" report "<AT-ID>" <<'JSON'
{"request_id":"report-sc1","scene_ids":["SC1"]}
JSON
```

查看旧项目的原始定义可用 [需求基线与测试场景](../definitions/entry.md) 的只读入口。报告链接指向实际生成的 `report.html` 与 `snapshot.json`。区分未执行、待独立复审、原证据缺失、旧版、产品缺陷、需修订和通过。只跑部分用例时交付该范围；场景通过需要全部必要义务、当前版本和对应独立证据。只查看或报告任务结束于交付链接。

用户要在浏览器持续查看时，可运行 `node results.mts --root <项目> serve <AT-ID>`，给出该进程实际返回的本机 URL。看板每 5 秒读取已落盘记录，按需求和场景分组，同一验证项与对应的执行和独立复审在同一行。一个场景关联多条需求时，各组都可跳转到同一份记录。搜索和状态筛选保留关联对象。点需求可读到基线原文，点场景可读到测试场景原文。记录快照编号用于追溯。点用例、执行或复审可查看对应的检查项、运行信息或意见，并沿关系打开原始证据。 正式验收尚无执行记录时，按最新可用调试收据显示待设计复审、复审未放行或待正式执行。点击设计复审可查看原因。调试不计入正式执行次数或交付结论。更新时保留打开的详情，用户可以按提示更新。需要可分享的离线副本时使用报告导出。

用 TDD 验收 ID 打开看板时，执行列标记红灯或绿灯，独立结论显示预期红灯确认或绿灯复审。绿灯结果以 TDD 结论展示。

用例列表按业务标题展示，编号和自动或人工类型放在标题下方。用例概览按关联场景、前置条件与数据、步骤与预期结果分区。旧记录可在用例概览查看同组用例的前序步骤作为参考。源码、断言和设计复审放在「依据与记录」，正式执行和独立复审各有详情入口。场景概览分别展示关联需求、验证范围、验收判据及关联用例入口。场景原文和检查缺口在「依据与记录」。有判据分组时按主题展示。历史判据里的列表标记按单层列表渲染，完全重复的验证范围在概览中只显示一次。离线报告同样将场景判据和用例步骤分开。

需求级状态取决于范围核对和所有关联场景。场景下分别显示自动用例与人工验证项。打开验证项的「关联关系」可访问同一 ID 的多次执行。每次执行的详情保留版本、文件摘要、实际结果、自己的证据和独立复审。当前结果随最新适用收据更新，历史执行仍可访问。

同一个 ID 跨阶段沿用时，可在看板顶部切换 TDD 开发和正式验收。启动服务时用 `--phase development` 或 `--phase acceptance` 选择初始视图。正式验收看板只用本阶段收据判断运行与通过状态。

维护盘点使用 `node results.mts --root <项目> serve-inventory`。看板在场景后列出关联用例及源码位置，并分别显示执行证据、交付状态和下一步。旧报告缺少 `cases` 时显示「未记录用例关联」。看板等待实际的 `.acceptance-local/native-v1/inventory.json` 落盘。

## 截图与落盘核对

每步先完成实际操作，重新读回落盘数据核对，再在看板或当前操作界面截图。用递增序号、需求 ID 或场景 ID、步骤名保存图片。需求基线记录、场景来源沿用核验和最终交付各保存一张。每条需求的缺口结论以及每个场景的匹配、准备、运行、复审或阻塞都要有各自的记录，适用几步就留下几步。

同目录保存 `checkpoints.json`，逐步记录 `step`、`requirement_id` 或 `scene_id`、记录快照摘要、实际数据位置、核对结论和截图相对路径。范围步骤核对需求基线来源、需求与场景集合和新增 ID。场景步骤核对场景和用例 ID、当前版本，以及适用的命令、退出码、日志摘要或复审结论。盘点逐条核对落盘项、用例定位及历史证据适用性。看板等到本步数据已刷新后再截图。遇到阻塞也截图和记明原因。无截图能力时如实标记缺失。

进入下一条前核对当前条目已留下结论和证据。最后对照需求基线和当前测试场景清单，确认每条需求与每个场景都各有明确状态。被授权缩小范围时记录排除项及理由。
