# 依据与定义

使用本包的 [记录工具](../../scripts/records.py)。命令示例中的 `<脚本>` 为该文件的绝对路径，`<项目>` 为Git 仓库根目录。在应用位于子目录时，使用从 Git 根起算的路径。脚本使用 Python 3.10+，只处理本地记录。

## 选择操作

1. `python3 <脚本> --root <项目> current` 查看新版与旧版当前指针。新版写入 `.acceptance/native-v1/` 与 `.acceptance-local/native-v1/`。查询旧验收用 `show <AT-ID> --legacy`，只读展示已有定义与记录路径。新版查询用 `show <AT-ID>`。以实际返回为准。
2. 新建时用 `create <AT-ID> --request <用户实际请求> --reference <来源>`。用户给出 ID 时，按原样使用。例如「新建 AT-file」必须传入 `AT-file`。只有未指定 ID 时才分配新 ID。保留用户原话。消息 ID 不可取得时，使用「当前用户消息」这样的真实来源描述。仅创建时在取得身份后停止。已有新版验收可以用 `start <AT-ID>` 选中，当前已有另一活动验收时报告冲突。
3. Git 项目需要实际忽略 `.acceptance-local/native-v1/`。工具会核对。用户授权准备仓库忽略规则时可先补充该规则，其他情况提示具体阻塞。

## 冻结需求与场景

- 核对用户指定的文件、范围和实际文字。范围明确后，对每个选段调用 `source <文件> <起始行> <结束行>`，行号含两端。用命令返回的完整对象作为该项的 `source`。冻结多项时，直接解析命令输出的 JSON 并组装请求，避免转抄时改变行尾或转义字符。口头需求使用 `{"kind":"user","reference":"当前用户消息","text":"用户实际提出的需求原话"}`。
- 需求和场景应一致，场景明确关联已冻结或本次同时冻结的需求。遇到矛盾或范围歧义，给出具体出处并停止冻结依赖项。已有 ID 的定义需要改动时，取得明确授权后在该项记录实际授权原话。工具校验版本和引用，Agent 负责业务含义与授权判断。
- 用 `show` 核对当前版本，再通过下例的 heredoc 将完整请求传给工具。首次执行 `freeze` 就传入完整 JSON。新请求使用新 `request_id`，重试同一请求使用同一份输入。首次冻结的 `base_sha256` 为 `null`，后续用当前 `definitions.sha256`。

```sh
python3 "<脚本>" --root "<项目>" freeze "<AT-ID>" <<'JSON'
{
  "request_id": "freeze-r1",
  "base_sha256": null,
  "requirements": [
    {"id":"R1","source":{"kind":"user","reference":"当前用户消息","text":"用户实际提出的需求原话"}}
  ],
  "scenarios": []
}
JSON
```

场景项形如 `{"id":"SC1","requirements":["R1"],"source":{...}}`，其中 `source` 必须是实际取得的完整来源对象。指定修订时加 `revision_authorization`，保留具体授权。

收到 `frozen` 或 `already_frozen` 后，交付实际版本、位置、选定需求及场景，并更新计划。历史请求返回旧版本时如实说明适用性。若返回 `scenes_needing_revalidation`，指出受影响场景。冻结操作按用户停止点结束。

## 交付场景推导

TDD 先冻结已确认需求及已有验收点。盘点和正式验收先查当前范围是否已有完成场景缺口核对的冻结记录。用 `results.py view <来源 AT-ID>` 查看 `scope_reviews`，并核对本次需求、验收点原文与冻结依据。可沿用的需求保留既有场景 ID、来源及已核验的用例关联。同一验收可直接续用定义。必须新建时引用来源验收 ID、版本和记录路径，保留场景和用例身份，再核对当前测试声明。只有范围尚未核对的需求进入补齐分支。已有用例、偶然发现的补充场景或执行通过都不能替代场景范围核对。旧记录有明确逐需求核对证据时可核验后采用，并在本轮记录来源。

进入补齐分支时，先单独冻结已有需求和原验收点，保存该基线版本及截图。按需求顺序处理，每条单独核对：

1. 列出原验收点的实际输入与可观察结果。把需求明示的下界、上界、阈值和异常类别分别对照这些输入。在范围核对收据中列出每项对应的现有场景或补充场景。区间一端的样例只覆盖该端。未被现有用例直接验证的明示边界应补场景，除非能指出实际覆盖该边界的等价断言。也检查会改变结论的状态转换或安全风险。
2. 对发现的缺口写明关联需求、为什么值得验证、初始条件、动作和可观察结果。明确标为「补充场景」，每场景独立小节，通过 `source` 引用后追加冻结。原验收点保留原 ID 和引用。涉及新产品约定时记录待确认，相关需求的范围核对保持待办。
3. 对这一条需求用 `operations.py --root <项目> analyze <AT-ID>` 记录范围结论。输入示例如下。无缺口也记录判断依据，`scenario_ids` 列全当前场景。工具计算相对原冻结基线新增的场景。核对收据、截图后进入下一条需求。

```json
{"request_id":"scope-r1","definitions_sha256":"当前定义摘要","requirement_ids":["R1"],"analysis":"实际核查依据和补齐或无缺口的结论","scope_review":{"baseline_sha256":"原验收点冻结摘要","scenario_ids":["SC1","SC4"]}}
```

场景阶段以最终冻结的场景清单和逐需求范围核对结果为交付物。列明需求关联及待确认项。用例匹配、编写、调试和执行各有独立产物，按本轮范围进入。同一场景关联多条需求时执行一次，在各需求下引用同一场景结果。范围核对凭证绑定单条需求和它的场景，其他需求的追加冻结不会使它失效。场景或需求内容变化时重新核对受影响范围。
