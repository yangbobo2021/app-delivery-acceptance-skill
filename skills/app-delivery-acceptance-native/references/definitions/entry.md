# 需求基线与测试场景

使用本包的 [记录工具](../../scripts/records.mts)。命令示例中的 `<脚本>` 为该文件的绝对路径。Git 项目从用户指定的工作目录运行 `git rev-parse --show-toplevel`，直接用它返回的路径作为 `--root`；非 Git 项目用指定的项目目录。后续登记沿用同一个根目录，收据里的相对路径也从这里解析。脚本用 Node.js 24.12+ 直接运行，只处理本地记录。

## 选择操作

1. `node <脚本> --root <项目> current` 查看新版与旧版当前指针。新版写入 `.acceptance/native-v1/` 与 `.acceptance-local/native-v1/`。查询旧验收用 `show <AT-ID> --legacy`，只读展示已有定义与记录路径。新版查询用 `show <AT-ID>`。以实际返回为准。
2. 新建时用 `create <AT-ID> --request <用户实际请求> --reference <来源>`。用户给出 ID 时，按原样使用。例如「新建 AT-file」必须传入 `AT-file`。只有未指定 ID 时才分配新 ID。保留用户原话。消息 ID 不可取得时，使用「当前用户消息」这样的真实来源描述。仅创建时在取得身份后停止。已有新版验收可以用 `start <AT-ID>` 选中，当前已有另一活动验收时报告冲突。
3. Git 项目需要实际忽略 `.acceptance-local/native-v1/`。工具会核对。用户授权准备仓库忽略规则时可先补充该规则，其他情况提示具体阻塞。

## 记录需求基线和测试场景

- 核对用户指定的文件、范围和原文。范围明确后，对每个选段调用 `source <文件> <起始行> <结束行>`，行号含两端。直接用返回的完整对象作为该项的 `source`，组装请求时保留原文。口头需求使用 `{"kind":"user","reference":"当前用户消息","text":"用户实际提出的需求原话"}`。
- 以用户已确认的需求作为验收基线。测试场景关联基线中的需求，可在本轮授权内补充或修订。遇到矛盾或范围歧义，给出具体出处，暂停依赖该结论的工作。需求内容有变化时，按用户确认的内容更新需求基线。
- 用 `show` 的 `definitions.path` 读取当前记录快照，再用下例的 `freeze` 命令保存。这是记录工具的兼容命令，既能记录需求基线，也能保存场景变更。新请求使用新 `request_id`，重试使用同一份输入。首次保存时 `base_sha256` 为 `null`，后续直接取 `show` 返回的 `definitions.sha256`。

```sh
node "<脚本>" --root "<项目>" freeze "<AT-ID>" <<'JSON'
{
  "request_id": "freeze-r1",
  "base_sha256": null,
  "requirements": [
    {"id":"R1","source":{"kind":"user","reference":"当前用户消息","text":"用户实际提出的需求原话"}}
  ],
  "scenarios": []
}
JSON
```

保存新建或修订场景时，场景项同时记录原始依据和可独立阅读的业务判据。

```json
{
  "id": "SC1",
  "requirements": ["R1"],
  "source": {"kind":"user","reference":"当前用户消息","text":"同一会议室已有预约时，部分重叠的预约应返回 409，且不得改变已有预约。"},
  "scenario_scope": {
    "title": "重叠预约拒绝与状态保护",
    "behavior": "同一会议室已有预约时，验证部分重叠的预约会被拒绝。",
    "criteria": ["部分重叠的预约返回 409。", "已有预约集合和各条记录的字段值保持不变。"]
  }
}
```

`source` 保留实际取得的完整来源对象。将原文中的适用业务状态和待验证行为写入 `behavior`，每条判据写一个能独立判断的业务结果。需求规定的状态码、阈值、副作用和真实浏览器等验证条件要保留。具体账号、样例数据、命令、操作顺序和证据采集方法留给用例设计。已有验收点如果写成操作清单，完整保存在 `source`，逐项提炼其中的业务预期。比如「用旧账号登录，检查原课程查询为未报名」可提炼为「迁移前已有账号与课程的组合视为从未报名」。对照原文，避免新增产品约定或丢失约束。

每个判据只填正文。标题、列表符号、编号和「验证下列结果」等引导句放在判据之外。普通场景用 `criteria` 数组。保留原场景 ID 时，如需区分多个验证主题，可用有序的 `groups` 替代 `criteria`，例如 `"groups":[{"title":"历史数据保留","criteria":["原账号和课程的 ID 及数据保持不变。"]},{"title":"迁移后的报名状态","criteria":["既有账号与课程的组合视为从未报名。"]}]`。从原文逐项检查判据语义和分组，再保存。

旧场景可按现有记录继续使用。用户授权修订时再更新其结构化字段。修订已有 ID 时，用 `revision_authorization` 保留具体授权。若本轮任务已授权修订场景，引用本轮指令即可。

收到 `frozen` 或 `already_frozen` 后，交付本次采用的需求基线、涉及的测试场景和记录路径，并更新计划。记录快照编号用于追溯，当场景变动时也可能更新。历史请求返回旧快照时如实说明适用性。若返回 `scenes_needing_revalidation`，指出待重新核对的场景。按用户指定的停止点结束。

## 交付场景推导

TDD 先记录需求基线和已有验收点。盘点和正式验收先查当前范围是否已经核对过场景缺口。用 `results.mts view <来源 AT-ID>` 查看 `scope_reviews`，并对照本次的需求基线和已有验收点。可沿用的需求保留既有场景 ID、来源及已核验的用例关联。同一验收可直接续用当前记录。必须新建时引用来源验收 ID、记录快照和路径，保留场景和用例身份，再核对当前测试声明。只有范围尚未核对的需求进入补齐分支。已有用例、偶然发现的补充场景或执行通过都不能替代场景范围核对。旧记录有明确逐需求核对证据时可核验后采用，并在本轮记录来源。

进入补齐分支时，先记录需求基线和原验收点，保留工具返回的快照路径、摘要及截图。按需求顺序逐条核对。

1. 列出原验收点的实际输入与可观察结果。把需求明示的下界、上界、阈值和异常类别分别对照这些输入。在范围核对收据中列出每项对应的现有场景或补充场景。区间一端的样例只覆盖该端。未被现有用例直接验证的明示边界应补场景，除非能指出实际覆盖该边界的等价断言。也检查会改变结论的状态转换或安全风险。
2. 对发现的缺口写明关联需求、补充依据、要验证的业务行为和可观察的验收判据。补充输入或前置状态时，沿用原始依据规定的预期结果。保存前从用户确认的需求或项目约定逐项核对必测判据的依据；只有新场景自身写下的预期，作为范围外观察单列。已确认的要求本身有歧义时，记录待确认并保留相关待办。将新增场景标为「补充场景」，每场景独立小节，通过 `source` 引用后保存。补齐时只追加新场景，沿用快照里原有的场景记录。
3. 对这一条需求用 `node operations.mts --root <项目> analyze <AT-ID>` 记录范围结论。`scope_review.baseline_sha256` 取补齐前的工具收据，`definitions_sha256` 和 `scenario_ids` 取当前收据（多需求时，按当前快照中的关联筛出本需求的全部场景）。`freeze` 收据使用 `sha256`，`show` 使用 `definitions.sha256`；无缺口时两处摘要相同。核对收据、截图后进入下一条需求。

```json
{"request_id":"scope-r1","definitions_sha256":"当前记录快照摘要","requirement_ids":["R1"],"analysis":"实际核查依据和补齐或无缺口的结论","scope_review":{"baseline_sha256":"补齐前的记录快照摘要","scenario_ids":["SC1","SC4"]}}
```

场景阶段交付当前测试场景清单和逐需求范围核对结果，列明需求关联及待确认项。用例匹配、编写、调试和执行各有独立产物，按本轮范围进入。同一场景关联多条需求时执行一次，在各需求下引用同一场景结果。范围核对凭证绑定单条需求和它的场景，与其他需求无关。场景或需求内容变化时重新核对受影响范围。
