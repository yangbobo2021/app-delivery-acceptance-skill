# 正式执行、证据及返修

正式验收先按[场景范围](../definitions/entry.md#交付场景推导)沿用适用的测试场景及用例关联，或先记录原验收点再逐需求补齐。以需求组织下属场景的准备、独立设计复审、执行和独立执行复审。分别保存各场景和验证项的实际结论或阻塞，然后汇总到需求。

## 执行前更新 PLAN

每次启动正式执行或实际人工观察前，核对当前测试场景和即将执行的验证项，把准确 ID 用于操作请求和证据记录。单独调用原生 `update_plan`，把对应的简短业务动作标为唯一进行中条目，保留后续待办。等 PLAN 更新成功，再单独发起该次执行或观察。

正式执行可写「验证未报名学生无法播放」。同一人工验证项观察两次时，分别写「首次观察播放地址续签」和「再次观察播放地址续签」。首次完成后，先把第二次标为进行中，再启动第二次。每次观察各自调用并登记证据。

只执行用户选择的场景与用例。先核对需求基线与当前测试场景是否一致。冲突时保留两份依据并按权限停止。先从同一场景、当前记录快照和用例版本的独立设计复审取得设计有效结果。设计有效但已观察到真实产品缺陷时，仍正式执行有效用例并按实际结果复审。必要运行条件与覆盖证据适用后，每个自动用例先更新 PLAN，再用 [操作工具](../../scripts/operations.mts) 的 `execute <AT-ID>` 正式运行：

```json
{
  "request_id":"execution-v1","scene":"SC1","definitions_sha256":"<当前记录快照摘要>",
  "design_review":"<实际通过的设计复审 ID>","selected_case_ids":["<指定 TC>"]
}
```

工具根据已审用例命令逐项执行，保存退出状态、日志、运行时间和真实附件。测试可将需要随执行保存的附件写入 `ACCEPTANCE_EVIDENCE_DIR`。覆盖工具的原始结果和业务断言分开核对。执行结果可作为本轮交付物，按实际复审状态呈现。用于正式交付判定前，按[独立复审约定](reviewer.md)取得逐项意见。重跑部分用例时保留未重跑部分状态，不升级成整场景通过。

已登记的人工验证项按[执行前更新 PLAN](#执行前更新-plan)为每次实际观察更新进行中条目，再启动操作。用 `manual <AT-ID>` 保存每次实际操作。提交新的 `request_id`、`scene`、`definitions_sha256`、对应 `match`、`product_version` 和 `product_files`。在 `cases` 下以原验证项 ID 列出实际操作，每项含 `action`、`expected`、`observed`、`performed_by`、`performed_at`、`receipt_reference`、`outcome` 以及 `evidence` 路径和 SHA-256。复核时沿用同一验证项 ID，为本次操作使用新请求 ID，并分别提交实际附件及复审。

诊断类人工观察保留原始文案，并说明它表达的含义如何对应验收预期。按语义判定，含义等价即满足文案检查。只有需求基线明确指定语言或原文时，才额外核对该语言或原文。

复核用户指定的历史收据时，先用 `history <AT-ID>` 导入并保留现有材料，输入 `request_id`、`scene`、`definitions_sha256`、实际 `receipt` 路径和对应 `case_id`。工具核对原收据中的输入及输出摘要，并保存副本。先独立评估这份历史，确认意见与授权后再动相关测试。历史通过也需要按真实范围和旧版本展示。

| 复审结果 | 处置 |
| --- | --- |
| 测试缺口 | 依据实际意见，回到场景、自然语言设计或用例实现修订。从变更点重新取得匹配、调试、复审和执行证据。仅实现有问题时沿用原设计。 |
| 证据缺口 | 核对缺失的记录和能否补齐。确需重跑时仅在授权范围重跑，保留原证据。 |
| 定义冲突 | 记录两份依据并阻塞依赖项。以需求基线为依据修订受影响的场景。若需求需要变化，按用户确认的内容更新基线，再重做受影响部分。 |
| 产品缺陷 | 保留实际失败和独立意见。按授权的验收范围交付。 |
| 通过 | 保存指定范围对应版本和证据，正式验收继续做逐需求判定。 |

收到可修订的真实意见后，才追加该轮 PLAN 项。默认最多两轮自动测试修复。用户只要求指定检查点时，按已完成阶段交付实际路径和未完成项。

重试前根据已有证据说明本次要验证的新假设或改动，并遵守用户授权和本次时间或轮次上限。缺少可验证的下一步或已到上限时，结束该项尝试，保留原始证据并记录缺失的证据、阻碍、已做的尝试和续接条件。继续完成不依赖该项的执行、复审和判定。

## 逐需求交付判定

正式验收按[独立复审约定](reviewer.md#需求级交接)启动新上下文的需求级 Reviewer。正式执行出现可能违反必测判据的结果时，先完成影响该结论的前置检查，再优先复审该次执行。等待执行复审时，主 Agent 用当前正式记录准备需求原文、范围、版本、失败日志、未验证项以及判定请求 ID 和意见路径。独立执行复审确认当前版本存在产品缺陷后，补上已落盘的复审收据，下一步就交接并提交需求判定。项目要求的其他回归和补测继续作为交付工作。有时限时，为执行复审及需求判定预留时间。若超时，分别报告已由执行复审确认的缺陷和仍待完成的需求判定，并引用现有收据。

其余需求在已有证据完成复审、剩余缺口登记后交接。可一次交接多条需求，每条单独给意见。通过仍要求全部必测项有有效证据。只交付用户指定检查点的任务按原停止点结束。

对每条需求单独调用 `node operations.mts --root <项目> delivery-judge <AT-ID>`。先为该需求分配请求 ID，将同名意见文件路径交给 Reviewer，待它写入 `{"status":"<实际状态>","reason":"<实际依据>"}` 后再提交。

```json
{
  "request_id": "delivery-r1-v1",
  "definitions_sha256": "<当前记录快照摘要>",
  "requirement_ids": ["R1"],
  "reviewer_session": "<真实独立 Reviewer 会话 ID>",
  "review_file": ".acceptance-local/native-v1/<AT-ID>/review-inbox/delivery-r1-v1.json"
}
```

每条都读回实际 `delivery-judge/.../result.json`，核对 `status: "judged"`、单一需求 ID 和 `judgment.status`。工具拒绝提交时，核对请求 ID、同名意见文件、当前记录快照摘要与实际范围再提交。

收尾前运行 `node results.mts --root <项目> view <AT-ID>`。从 `requirement_results[需求].delivery_judgment` 读取有效收据和状态。后续补测或版本变化使先前判定失效时，保留原记录，用当前有效证据重新独立判定。末版 PLAN 每条需求保留业务名和简短结论，例如「课程报名通过验收」。完整收据路径写入交付结果。看板、离线报告和 `finish` 使用同一结果视图。已落盘的失败或受阻也按实际结论完成判定条目。缺少有效收据时显示待判定，说明原因并保留待办。
