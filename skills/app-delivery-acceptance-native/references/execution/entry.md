# 正式执行、证据及返修

正式验收先按[场景范围](../definitions/entry.md#交付场景推导)沿用已经补齐的场景及用例关联，或先冻结原验收点再逐需求补齐。以需求组织下属场景的准备、独立设计复审、执行和独立执行复审。分别保存各场景和验证项的实际结论或阻塞，然后汇总到需求。

只执行用户选择的场景与用例。先检查实际冻结需求和场景是否一致，即使它们已被标记为冻结。冲突时保留两份依据并按权限停止。先从同场景、当前定义及用例版本的独立设计复审取得设计有效结果。设计有效但已观察到真实产品缺陷时，仍正式执行有效用例并按实际结果复审。必要运行条件与覆盖证据适用后，用 [操作工具](../../scripts/operations.py) 的 `execute <AT-ID>` 正式运行：

```json
{
  "request_id":"execution-v1","scene":"SC1","definitions_sha256":"<当前摘要>",
  "design_review":"<实际通过的设计复审 ID>","selected_case_ids":["<指定 TC>"]
}
```

工具根据已审用例命令逐项执行，保存退出状态、日志、运行时间和真实附件。测试可将需冻结的附件写入 `ACCEPTANCE_EVIDENCE_DIR`。覆盖工具的原始结果和业务断言分开核对。正式执行结束后，按[独立复审约定](reviewer.md)取得逐项意见。重跑部分用例时保留未重跑部分状态，不升级成整场景通过。

已登记的人工验证项用 `manual <AT-ID>` 保存每次实际操作。提交新的 `request_id`、`scene`、`definitions_sha256`、对应 `match`、`product_version` 和 `product_files`。在 `cases` 下以原验证项 ID 列出实际操作，每项含 `action`、`expected`、`observed`、`performed_by`、`performed_at`、`receipt_reference`、`outcome` 以及 `evidence` 路径和 SHA-256。复核时沿用同一验证项 ID，为本次操作使用新请求 ID，并分别提交实际附件及复审。

诊断类人工观察保留原始文案，并说明它表达的含义如何对应冻结预期。按语义判定，含义等价即满足文案检查。只有冻结要求明确指定语言或原文时，才额外核对该语言或原文。

复核用户指定的历史收据时，先用 `history <AT-ID>` 冻结现有材料，输入 `request_id`、`scene`、`definitions_sha256`、实际 `receipt` 路径和对应 `case_id`。工具核对原收据中的输入及输出摘要，并保存副本。先独立评估这份历史，确认意见与授权后再动相关测试。历史通过也需要按真实范围和旧版本展示。

| 复审结果 | 处置 |
| --- | --- |
| 测试缺口 | 将实际意见交回用例设计。保存新版的调试、独立设计复审、正式执行及执行复审。 |
| 证据缺口 | 核对缺失的记录和能否补齐。确需重跑时仅在授权范围重跑，保留原证据。 |
| 定义冲突 | 记录两份依据并阻塞依赖项。明确授权后通过定义能力生成新版本，再重做受影响部分。 |
| 产品缺陷 | 保留实际失败和独立意见。按授权的验收范围交付。 |
| 通过 | 保存指定范围对应版本和证据，正式验收继续做逐需求判定。 |

收到可修订的真实意见后，才追加该轮 PLAN 项。默认最多两轮自动测试修复。用户只要求指定检查点时，按已完成阶段交付实际路径和未完成项。


## 逐需求交付判定

正式验收完成用例级复审后，逐条需求请独立 Reviewer 汇总本次范围、场景覆盖、自动执行、人工观察、对应复审和仍存在的缺口。用例级复审通过、未通过或因权限受阻，都进入这一步。Reviewer 按实际证据给出 `passed`、`failed` 或 `blocked`，写明依据。只交付用户指定检查点的任务按原停止点结束。

对每条需求单独调用 `operations.py --root <项目> delivery-judge <AT-ID>`。先为该需求分配请求 ID，将同名意见文件路径交给 Reviewer，待它写入 `{"status":"<实际状态>","reason":"<实际依据>"}` 后再提交。

```json
{
  "request_id": "delivery-r1-v1",
  "definitions_sha256": "<当前冻结摘要>",
  "requirement_ids": ["R1"],
  "reviewer_session": "<真实独立 Reviewer 会话 ID>",
  "review_file": ".acceptance-local/native-v1/<AT-ID>/review-inbox/delivery-r1-v1.json"
}
```

每条都读回实际 `delivery-judge/.../result.json`，核对 `status: "judged"`、单一需求 ID 和 `judgment.status`。工具拒绝提交时，核对请求 ID、同名意见文件、当前定义摘要与实际范围再提交。逐条把收据路径和实际结论保留在末版 PLAN 与交付结果中。缺少收据时把对应项标为受阻并说明原因，正式验收仍待收尾。
