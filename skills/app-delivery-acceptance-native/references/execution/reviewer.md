# 独立 Reviewer

每次启动 Reviewer 前，先定稿完整交接范围，再更新 PLAN。

1. 交接逐项列出需求、场景、验证项、版本或实际执行记录及证据路径。同一用例有两次执行时分别列出两个记录。需求级复审列出各需求及关联场景。
2. 用同一批目标生成简短的 PLAN 条目，例如「独立复审两次播放续签结果」。单独调用 `update_plan`，标记该项为唯一进行中条目，等待返回。保留其余待办和已完成结论。
3. 将完整交接传给 `spawn_agent`。核对交接明细、PLAN 的业务范围和数量相符。目标有变时，重新核对并更新 PLAN 后再启动。各条需求的结论收到后分别勾选。

把下面的问题直接写进候选设计 Reviewer 的启动消息。

> 先核对每条必测判据能否从已确认的需求或项目约定推出。判据本身增加了原始依据未规定的产品行为时，在 `reason` 指出该判据与原始依据，判为 `needs_revision`、`revision_target: scene`。再按[用例设计的边界检查](../case-preparation/design.md#边界检查)反查实际断言。如果实现只对当前样例正确，现有断言还能不能全过？在 `reason` 引用决定放行或退回的实际断言位置（文件及行号或可定位的语句）。用两个结果一致来证明必测行为时，在 `reason` 选一个会影响该判据的具体共同错误，按实际执行顺序代入相关断言。指出第一条能拦住它的断言及原因。若所有断言仍通过，引用现有比较的位置，说明为什么前置断言和比较都未拦住它。设计预期和正常调试日志不能代替实际断言。只有满足该节阻塞条件时，才在 `reason` 说明依据、漏掉的目标或状态和现有断言为何会放过它，判为 `needs_revision` 并指出最早需修订的环节。其余合理反例在 `reason` 中标为可选补测。调试通过或失败均用同一标准，已复现的有效失败照常登记。

同一版候选完成调试后，合并场景、设计、实现和调试证据交给同一位独立设计 Reviewer，在一轮意见中分别核对。准备阶段发现的疑点也放进这次交接，避免在调试前先启动一轮同范围复审。正式执行仍由另一位 Reviewer 核对。

主 Agent 使用宿主的原生子 Agent 调用，启动一位新上下文的 Reviewer，等待实际返回。Codex 的 `spawn_agent` 必须明确传 `fork_turns: "none"`。交接只提供任务、文件路径和需要核对的事实，不提供主 Agent 的判断或完整会话。Reviewer 对项目资料和证据只读，只能写自己本轮的意见文件。交接真实验收 ID、需求基线和采用的测试场景、项目测试约定、实际用例 ID、源码及候选版本、对应执行或调试结果和证据。需要图像判断时让 Reviewer 实际查看相关图片。以原始材料判断，独立确认每个 TC 的覆盖边界和原始证据。

交接用例或观察收据时，为每个验证项列明它负责的检查项 ID、原文、预期和证据路径。已有用例参考匹配收据中该项的 `cases[ID].covers`，执行复审同时核对已审设计分配给该项的检查。自动项按实际断言及运行证据判断，人工项按本次操作的预期和原始观察判断。场景总义务用于核对整体覆盖。若文案内容由人工项验证，自动项按它负责的退出状态和输出契约判断。把跨验证项或整场景的缺口写进场景结果，需要需求级判定时一并交接。若分工与需求基线冲突，指出具体出处。

候选复审分别回答两件事。先从需求基线和采用的测试场景反查[自然语言用例设计](../case-preparation/design.md)，对照原始依据核对场景判据是否完整、准确，确认场景只表达业务行为、适用条件和判定结果，具体样例、命令和操作顺序已落在用例。再确认用例设计是否逐项验证，预期是否准确。再对照设计核查实际输入、代码或人工步骤、独立断言和[探针自检](../case-preparation/implementation.md#探针自检)。在 `reason` 分别写明两项结论。新版候选若需修订，补 `revision_target`，用 `scene` 表示场景漏掉需求行为或把用例操作写进判据，并指出相关判据原句，`design` 表示场景已要求但自然语言设计遗漏或判据有误，`implementation` 表示代码、人工步骤或探针偏离已写设计。若一项有多处问题，按最上游需修订的阶段标记，并说明其余问题。没有适合承接漏项的实际用例时，在同场景候选意见中指出漏项，覆盖认领仍限各自已分配的检查。执行复审逐项核对实际结果和副作用，区分证据缺失、测试故障及产品缺陷。

替换或拆分已有用例时，设计交接附原始声明位置和检查去向。Reviewer 先读需求基线条款与旧声明的实际输入和断言，再从来源反查匹配清单与候选断言，在现有意见中引用复核的原始位置和检查去向。若本次范围内可各自失败的检查漏列、缺少对应断言或无依据被排除，即使现有候选均通过，也对负责该检查的候选给出 `needs_revision`，指出漏项和来源。

执行复审和需求级复审对诊断文案采用同一判据。引用原始输出并核对其含义，含义等价即满足文案检查。若需求基线明确指定语言或原文，额外核对该语言或原文。

先为这一轮选定 `review-v1` 等唯一请求 ID。先创建意见目录，向 Reviewer 提供仓库根路径和完整目标文件路径。请 Reviewer 自己写入 `.acceptance-local/native-v1/<AT-ID>/review-inbox/<请求ID>.json`，并报告写入结果。批量交接时每份目标收据预先分配独立请求 ID 和意见文件，文件名与请求 ID 一致。每份 JSON 只包含对应目标收据里的实际 TC。启动消息注明目标阶段，并附下方适用的意见样例和该收据中实际分配给各用例的检查 ID。

调试复审发现需修订的场景时，使用现有 `revision_target` 字段。

```json
{"cases":{"<TC-ID>":{"status":"needs_revision","revision_target":"scene","reason":"需求还适用于另一种前置状态，当前场景没有覆盖","covers":["<已支持的检查 ID>"]}}}
```

调试复审确认设计与实现有效、但发生产品失败时，使用现有 `design_status` 字段。

```json
{"cases":{"<TC-ID>":{"status":"product_defect","design_status":"valid","reason":"两项断言均有设计和实现依据。日志显示首项失败，后续项未到达。","covers":["<首项检查 ID>","<后续检查 ID>"]}}}
```

正式执行复审按实际运行证据写意见。

```json
{"cases":{"<TC-ID>":{"status":"product_defect","reason":"原始日志显示首项失败，后续项未到达。","covers":["<首项检查 ID>"]}}}
```

可用结论为 `passed`、`needs_revision`、`product_defect`、`definition_conflict`、`insufficient_evidence`。优先从目标收据的 `case_obligations[TC-ID]` 读取分配项。调试复审给出 `passed` 或 `design_status: valid` 时，`covers` 列出全部已由设计和实现证实覆盖的分配项，同时在 `reason` 区分实际执行到的检查和未到达的检查。正式执行复审的 `covers` 只列有本次实际执行证据的分配项。工具拒绝越界认领时，请原 Reviewer 用新请求 ID 出具修正意见，保留原文件。未看到独立意见、缺少实际图片或没有对应版本时，将待复审或阻塞如实记录。

原始依据规定首次写入值应匹配独立预期时，核对候选是否在规定的字段和观察面逐项断言，遗漏时给出具体字段和位置。原始依据只要求后续查询与创建响应一致时，核对候选是否查到实际创建的目标并比较规定的字段和值。

由主 Agent 从工具返回取得真实 Reviewer 会话 ID。以意见文件的文件名（去掉 `.json`）作为 `request_id`。用程序直接读取目标 `result.json` 字节计算 SHA-256 并填入请求，用 [操作工具](../../scripts/operations.mts) 的 `review <AT-ID>` 记录。工具直接读取 Reviewer 自己写出的文件并保留原始字节，主 Agent 只传路径。

```json
{
  "request_id":"review-v1","scene":"SC1","definitions_sha256":"<当前记录快照摘要>",
  "target_operation":"debug","target":"<实际调试 ID>","target_sha256":"<实际调试结果摘要>",
  "reviewer_session":"<真实子 Agent ID>","review_file":".acceptance-local/native-v1/<AT-ID>/review-inbox/review-v1.json"
}
```

在 `debug` 中，若用例和证据有效、失败已确认来自产品，同时写 `"status":"product_defect","design_status":"valid"`。这允许同版测试进入正式执行。正式执行复审按实际产品结论使用 `product_defect`，省略 `design_status`。

目标操作可为 `debug`、`execute`、`history`、`manual`、`tdd-red` 或 `tdd-green`。`tdd-red` 只在实际日志证明测试因需求基线规定的行为缺失而失败时使用 `expected_failure`。环境错误、测试错误和错误预期要分别说明，均不得授予 `expected_failure`。记录工具核对证据、实际用例集、版本和返回格式。主 Agent 依据宿主真实父子会话轨迹确认独立身份，按返回原样保存。

## 需求级交接

单独用 `spawn_agent` 加 `fork_turns: "none"` 启动需求级 Reviewer。一次可交接多条需求，用各自的请求 ID 和文件写意见。设计或执行 Reviewer 的上下文属于前一阶段。

按需求交接需求基线原文、选定范围、相关场景、实际用例与人工记录、执行复审收据、同版证据入口及已知缺口。有源码且可能用于说明覆盖范围时，附实际候选文件路径和版本。Reviewer 核对每条需求的完整范围，在 `reason` 中区分实测与推论。其余范围若由同版实现或其他证据支持，引用实际材料；依赖源码时，在 `reason` 引用实际代码路径，说明需求范围内的输入在什么条件下会进入相关分支、进入后会产生什么结果，以及未实测的差异是否会影响分支命中或结果。独立核实当前正式证据已证明任一必测判据失败时，判 `failed`，引用该证据并分别列出其余缺口。若尚无法确认失败且证据不足，判 `blocked`，指出哪个与需求有关的条件可能改变结果，以及现有证据为何无法排除该缺口。符合范围且证据充分时判 `passed`。
