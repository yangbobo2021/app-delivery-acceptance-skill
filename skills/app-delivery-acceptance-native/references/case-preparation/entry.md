# 已有用例匹配

核对用户指定的当前验收、当前测试场景和当前[自然语言用例设计](design.md)。读实际测试声明、输入、断言、辅助方法和跳过条件。按设计中的检查 ID 关联实际断言，说明检索入口、有效匹配和缺口。标题相似、作者自述和已有绿灯不足以证明覆盖；跳过的用例单列。

若用新用例替换或拆分旧用例，先从旧声明的实际输入和断言找出与需求基线条款相关、可各自失败的检查。把它们逐项记在匹配的 `search_scope` 或其引用的现有设计交接中，附原始文件行号和去向：沿用（用例与断言）、替代（新用例与断言），或排除（范围或等价依据）。旧断言不完整时，保留该检查为缺口，按需求基线条款补足判据。

以 [定义记录工具](../../scripts/records.mts) 的 `show` 获取当前 `definitions.sha256`，再用 `source <文件> <首行> <末行>` 取得用例对应完整声明的实际来源对象。检查过但未采用的文件也留实际摘要。用 [操作工具](../../scripts/operations.mts) 保存关联：

```sh
node "<操作工具绝对路径>" --root "<项目根>" match "<AT-ID>" <<'JSON'
{
  "request_id": "match-sc1",
  "scene": "SC1",
  "definitions_sha256": "<实际记录快照摘要>",
  "case_design": "<当前设计请求 ID>",
  "search_scope": "<实际检查过的范围及限制>",
  "inspected": {"tests/test_product.py":"<实际文件摘要>"},
  "cases": [{
    "selector":"<项目的实际声明定位>",
    "status":"active",
    "source": {"kind":"file","path":"tests/test_product.py","first":5,"last":16,"sha256":"<实际文件摘要>","text":"<source 返回的精确原文>"},
    "covers":{"state":"<选段内实际断言原文>"}
  }]
}
JSON
```

无匹配时使用空 `cases`，保留已检查的文件和缺口。`case_design` 绑定当前设计，工具从该收据读取检查清单。工具核验来源、版本及引用；断言的行为是否等价由实际代码和复审判断。已经有永久用例 ID 时沿用，其余使用声明定位得到的登记 ID。仅匹配任务以 `execution_status: not_executed` 结束，明确「全覆盖／部分覆盖／无匹配」是对本次场景检查而言。旧验收在续接已存在的旧匹配或复审时，可沿用其收据；若为该场景补录自然语言设计，后续匹配与执行切换到新版。

用户只允许盘点已有用例，且场景尚无设计时，可按当前场景判据用 `obligations: [{"id":"检查 ID","quote":"场景判据原句或片段"}]`（旧场景未单列判据时引用场景原文） 替代 `case_design` 做匹配，交付范围和缺口。后续进入新用例准备时先落盘自然语言设计，再按设计重做匹配。

正式验收沿用 TDD 场景时，先查同场景 `tdd-green` 收据的 `cases` 和 `test_bindings`。确认实际声明与该用例一致后，匹配条目加 `"tdd_case":{"green":"<实际绿灯请求 ID>","case_id":"<原 TC ID>"}`。跨验收时同时填原 `acceptance_id`。有原始声明选段时复用同一选段。旧收据无选段时结合测试声明、命令和独立复审核对。工具验证当前测试场景和测试文件字节，匹配结果保留原 TC ID 及收据引用。正式执行和复审使用匹配返回的 ID。

人工验证项也用 `match` 登记。条目加 `"kind":"manual"`，用实际检查步骤及预期所在的文件选段作为来源和覆盖依据。人工项与自动用例均保留原 ID，调试和正式自动执行只提交自动用例。
