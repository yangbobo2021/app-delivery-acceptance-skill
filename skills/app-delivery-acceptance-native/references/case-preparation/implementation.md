# 用例实现、调试与复审

开始匹配或编写测试前，先读回当前场景的[自然语言用例设计收据](design.md)，核对要实现的检查和仍待处理的缺口。用[匹配](entry.md)核对已有代码，逐项确认实际前置条件、业务输入、操作与断言是否兑现设计。能保留的用例沿用原 ID，按授权补充未实现的检查。只有标题相似、只发出了请求、或只断言了部分结果时，保留对应缺口。一个设计可以由多个实际用例实现，一个实际用例也可验证多个设计检查。

需要写测试时，先核对[运行和覆盖准备](environment.md)。Git 项目需要隔离候选时按[生命周期](../lifecycle/entry.md)绑定工作树，匹配、环境、测试修改和调试在同一候选目录。用户明确要求在当前工作区修订时，按其实际授权范围操作。

期望值来自需求基线和独立夹具。比如首次创建记录时，对实际输入中的业务字段逐个验证响应及首次持久化结果。两个产品返回相等只能证明一致性。比较拒绝前后状态时，核对设计要求的完整集合、数量及字段。实现发现设计或场景漏项时，记录原始出处并回相应阶段修订，使用新设计收据重新匹配。仅修代码时沿用当前设计，按新源码重新匹配。

把可能各自失败的业务检查设计成能独立运行或独立记录结果的单元。一个用例同时验证多项独立义务时，先核对前面的失败会不会让后续断言跳过。若会，按可独立运行的业务检查拆开；可共享夹具或运行准备。

调试或正式执行遇到提前退出时，从实际日志和代码标出已执行、已失败及未到达的检查。保留首个已证实的缺陷，单独执行仍能独立验证的未到达检查。后续检查依赖失败的前置条件时，记录实际阻塞原因。复审和报告只认领已经运行并有原始证据支持的检查。

## 探针自检

先在已知结果的样本上验证新探针的夹具、数据提取和断言，再依靠它判产品结果。优先用同一探针跑正常路径。若该路径也受候选缺陷影响，可用已知输入与预期的本地样本验证辅助函数和断言。记录命令、预期和实测。比较数据库等驱动返回的记录时，在断言前把参与比较的两边转成一致的普通字段结构，保留判定涉及的字段、值、类型和行数。自检失败先修探针并重跑，原日志保留为测试问题。

补写或修订后，按最终实际代码保存新的匹配收据，登记新增用例及实际断言，再用 [操作工具](../../scripts/operations.mts) 的 `debug <AT-ID>` 跑真实候选。始终使用当前匹配收据中的稳定 TC ID。请求示例：

```json
{
  "request_id":"debug-v1","scene":"SC1","definitions_sha256":"<当前记录快照摘要>",
  "match":"<实际匹配请求 ID>","runtime":"<实际运行准备 ID>","coverage":"<实际覆盖准备 ID>",
  "cases":{"<TC-ID>":{"command":["<已就绪的 Python>","tests/check_s1.py"],"files":["tests/check_s1.py"]}}
}
```

已授权关闭时传 `coverage_policy: "off"` 和实际 `coverage_basis`。每个 ID 的命令只执行其所表示的用例。调试收据保存源码副本、实际结果和证据。若用户给出已有调试候选，先核对当前版本和现有收据，再决定是否需要重新调试。

按[独立复审约定](../execution/reviewer.md)启动 Reviewer，交接实际定义、自然语言设计、匹配结果、项目测试规则、候选版本、调试证据和缺口。按复审指出的阶段修订，收到真实意见后才追加对应 PLAN。改动后以新请求调试、送审并保留旧版。默认最多两轮自动修订。只准备任务交付实际通过复审的用例、版本和其余缺口后停止。

已有候选待设计复审时，初始 PLAN 分别写清核对哪些业务用例、复审哪批测试设计。接到需修订意见后，保留首轮结论，再分别加入修订调试和新版复审条目。
