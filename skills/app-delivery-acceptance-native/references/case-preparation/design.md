# 自然语言用例设计

从需求基线、当前测试场景和项目测试约定出发。逐项反查场景的验收判据和原始依据，将每条必测判据落实到具体检查或记录缺口，为各项检查给稳定 ID。发现需求行为遗漏或依据冲突时，指出原文及影响，交回场景阶段。既有代码的范围只能用于后续匹配，不能缩小设计范围。

每个用例用自然语言写清业务标题、前置条件及数据、各检查的操作与输入、可核对的预期结果。人工项写到人能照做。一个用例可包含多个检查，可能独立失败的输入或预期用独立检查 ID 表达。检查拆成单独执行的用例时，在该检查的 `title` 写清它实际验证的业务行为，并用有序的 `setup` 列出共用前置条件之外的准备动作。用户应能按单条用例的说明复现检查。为未设计的检查记录具体原因。

从需求基线推导预期的业务值。一个操作在响应、后续查询或其他渠道分别呈现同一组业务数据时，逐个核对范围内的观察面及其预期。若某个观察面能独立出错，为它写出可直接比较的预期值，或明确说明范围依据。

用 [操作工具](../../scripts/operations.py) 的 `case-design <AT-ID>` 交付设计。该操作记录所依据的测试场景，以及检查与自然语言用例的关系，无需命令或源码。每个检查引用当前场景的验收判据原句或原句片段，逐组核对覆盖，分组标题本身不用作判据。旧场景未单列验收判据时引用场景原文。同一判据可支撑不同输入变体。只设计时读回收据，交付位置、已设计和未覆盖的范围后停止。

```json
{
  "request_id": "design-v1",
  "scene": "SC1",
  "definitions_sha256": "<当前记录快照摘要>",
  "obligations": [{"id":"reject","quote":"部分重叠的预约返回 409。"}],
  "cases": {
    "D-reject": {
      "title": "拒绝重叠预约",
      "kind": "automated",
      "preconditions": "空库中已有 A 室 10:00–11:00 的预约",
      "checks": [{"id":"reject","action":"向 A 室提交 10:30–11:30 的预约","expected":"响应 JSON status 为 409"}]
    }
  }
}
```

示例只展示一个检查。实际收据覆盖本轮的全部必测项。若某个检查暂时没有用例，仍列入 `obligations`，并在 `gaps` 中以其 ID 记录原因。设计修订用新的请求 ID，语义仍相同的用例和检查保留原 ID。设计 ID 用于描述和追踪，实际测试继续使用匹配收据的稳定 TC ID。

## 边界检查

对照需求基线和当前测试场景列出会改变验收判定的输入变体。每项记录关联条款、具体输入、预期状态及内容或副作用、对应的设计用例 ID。按变体分配检查项 ID。同一场景判据可支撑多个检查项。记录待核对的变体。

接口若明确要求拒绝客户端指定其他身份，检查客户端实际可发送的身份载体。查询参数和可发送的请求体分别验证，包括只读请求。高层客户端无法发送时，用能发出该请求的低层客户端核实。校验签名或地址时，分别检查每个约束字段，保留其他字段原值。对标识字段分别检查改为另一个合法标识和改为超出合法取值域的值。必要时单独验证参数缺失。按验收依据原文分别断言状态码、返回数据及状态变化。依据冲突时记录出处，未执行的变体列为未覆盖并说明原因。
