# 用例生成、调试与设计复审

读实际项目测试约定、冻结需求和场景、[匹配结果](entry.md)及其中的缺口。先核对[真实运行和覆盖准备](environment.md)。到位后才在授权的测试文件中保留有效断言、补充遗漏义务。覆盖可关闭的任务须有明确依据，保存该依据。

在 Git 项目准备隔离候选时，先按[生命周期](../lifecycle/entry.md)创建并绑定所选版本的 worktree。匹配、运行准备、测试修改和调试使用同一候选目录。用户明确要求在当前工作区修订时，按其实际文件范围操作。

期望值来自冻结要求和独立夹具。逐项对照场景里的业务输入。若场景指定用某个房间、时间段和标题创建首条记录，就在代码里把首次返回及第一次持久化查询中的房间、开始时间、结束时间和标题与独立预期比较。两个产品返回互相相等只能证明一致性。然后再比较操作前后的完整集合、数量和各字段。保留每个用例实际启动方式、输入、断言和适用边界。

用 [操作工具](../../scripts/operations.py) 的 `debug <AT-ID>` 跑真实候选。复用已有测试时使用匹配收据中的稳定 TC ID。真正新增的用例分配新 TC ID，后续修订保留身份。请求示例：

```json
{
  "request_id":"debug-v1","scene":"SC1","definitions_sha256":"<当前定义摘要>",
  "match":"<实际匹配请求 ID>","runtime":"<实际运行准备 ID>","coverage":"<实际覆盖准备 ID>",
  "cases":{"<TC-ID>":{"command":["<已就绪的 Python>","tests/check_s1.py"],"files":["tests/check_s1.py"]}}
}
```

已授权关闭时传 `coverage_policy: "off"` 和实际 `coverage_basis`。每个 ID 的命令只执行其所表示的用例。调试收据保存源码副本、实际结果和证据。若用户给出已有调试候选，先核对当前版本和现有收据，再决定是否需要重新调试。

按[独立复审约定](../execution/reviewer.md)启动设计 Reviewer，交接实际定义、项目测试规则、候选版本、调试证据和缺口。只有收到当前候选需修订的真实意见后，才在计划中加入本轮修订及复审。改动后以新请求调试、送审，保留旧版，直到当前用例都通过或达到用户授权和预算的边界。默认最多两轮自动修订。只准备任务交付已通过设计复审的用例和版本后停止。

已有候选待设计复审时，初始 PLAN 使用「核对当前候选与证据」「取得独立设计复审」两个实际步骤。接到需修订意见后，保留首轮结论，再分别加入「修订并重新调试」和「独立复审新版」。
