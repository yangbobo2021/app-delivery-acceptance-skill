# 架构与数据约定

## 使用入口

首个可安装候选版拟使用 `app-delivery-acceptance-native`，方便在同一台机器上与现有 Skill 对照。用户通过一个主 Skill 表达任务，例如「以 `docs/requirements.md` 的 R1 为需求基线，沿用 `docs/scenarios.md` 的 SC1，只找已有用例」或「对 SC1 补齐用例，运行并出验收报告」。同一任务可以后续补充授权或缩小范围。

主 Skill 提取项目位置、目标、选定对象、授权和停止点，结合已有资料选择直接能力。普通能力由当前 Agent 读取包内入口后执行。每层只约定自己的直接子能力。需要独立判断时，由调用层启动新的只读 Reviewer，交给它实际材料和所审版本，并等待真实结果。

## 包内组织

以下是实现目录。每个能力的短入口声明职责、前置输入、结果和停止条件，详细规则按需读取。

```text
skills/app-delivery-acceptance-native/
  SKILL.md
  references/
    definitions/           # 创建验收、需求基线、测试场景及变更
    case-preparation/      # 匹配、补缺、调试、独立设计复审
    execution/             # 正式执行、取证、执行复审及返修协调
    results/               # 当前与历史结果、报告、归档
    lifecycle/             # 启动、续接、恢复、知识、回填和清理
  scripts/                 # 本地数据读写、校验、取证和报告生成
tests/
  fixtures/
  contracts/
  e2e/
```

运行环境和覆盖环境是可复用的包内能力，由用例准备或正式执行按需调用。只准备环境也是有效停止点。脚本承担可重复的文件与数据操作、项目命令运行和结果核验。分支选择、权限判断及何时结束由 Agent 依据业务规则与实际返回作出。安装和使用走标准 Skill 入口，运行依赖是宿主能力和被测项目实际需要的工具。

| 能力 | 输入及交接 |
| --- | --- |
| 需求基线与测试场景 | 按指定文件、段落或用户原话记录已确认的需求基线，补齐测试场景并保留来源。记录快照供历史追溯。只创建可交付空验收。 |
| 用例准备 | 读取已确认场景、项目规范和授权。仅匹配模式返回实际候选、每个候选支持的场景义务及缺口。匹配后补充模式先完成匹配，再凭真实就绪的测试及覆盖环境补齐缺口，交付当前用例、调试证据与独立设计意见。 |
| 环境准备 | 交付真实测试入口、项目版本及运行检查结果。覆盖准备通过一次可核对的采集探测，证明实际产品进程被纳入。项目及采集条件变化后重查相应就绪证据。覆盖必须时，采集不可用则阻塞依赖它的工作，按原版可关闭覆盖的任务保留用户选择及理由。 |
| 正式执行 | 接收选定场景或 TC、当前用例和就绪条件。逐用例记录实际命令、执行范围、版本、环境、时刻、退出状态、日志及必要原始附件。适用时保存覆盖工具原始输出、采集范围和汇总。 |
| 独立执行复审 | 读取当次采用的需求基线和测试场景，以及每个执行用例、结果和原始证据。可批量交付，结论须逐 TC 归属。要求画面时传入实际可读的图像。作者自检、设计复审和正式执行复审各自保留。 |
| 报告 | 从对应版本的正式记录生成场景、用例及需求级视图，可展开历史与原证据。报告请求可单独完成。重跑一个 TC 的结果按实际范围展示，整体验收根据所有必要义务和同版证据判断。 |

## 返修与 Codex PLAN

主 Skill 在执行前用 `update_plan` 发布已知的本次步骤。完成一个可验收步骤后，依据实际结果更新进度。发现缺项或真实复审意见时，加入本次实际需要的步骤。独立 Reviewer 交回结论，由当前 Agent 更新同一张 PLAN。进入一个能力的内部循环时，仅在需要让用户看到实质进展的地方增加条目。

例如首轮复审要求补证据时，将它勾成「复审 v1（需修订）」，再加入「补充证据」「重新执行受影响用例」「复审新证据」。每一勾对应已经完成的工作，复审通过与否写在条目和原始记录中。发生阻塞时记录原因，未执行的依赖项保留待办。用户只准备用例时，计划在当前设计结果处结束。

| 复审发现 | 后续工作 |
| --- | --- |
| 用例不足 | 在授权和轮次内修订相关用例，重新调试、正式执行受影响范围并独立复审。 |
| 证据不足 | 补齐对应证据，必要时重跑受影响 TC，再复审同版结果。 |
| 需求或场景冲突 | 记录发现并暂停依赖该结论的操作。按需求基线和本轮授权修订场景。涉及需求变更时按用户确认的内容更新基线，仅重做受影响的下游。 |
| 产品缺陷 | 保留真实失败并报告。产品修复须有单独授权。 |
| 通过 | 交付本次授权范围，保存同版结果并停止。 |

## 被测项目的数据

延续原版可共享验收资料与本机运行资料分开的约定。为并行试用，设计稿使用 `native-v1` 写入命名空间，阶段 1 要验证旧查看器与新版共用目录时的发现和隔离行为，再确定具体布局。旧项目记录通过只读映射使用，保留来源、原版本和证据路径。缺少原证据时，展示相应缺项。

```text
<被测项目>/
  .acceptance/
    <旧验收资料>
    native-v1/
      <AT-ID>/
        manifest.json
        definitions/<记录快照>/
        cases/<scene-id>/       # 匹配与调试索引
        records/<scene-id>/     # 执行与复审索引
        records/archive-<id>.zip # 用户明确选定的归档
  .acceptance-local/           # 检查实际 Git 忽略规则
    native-v1/
      current.json
      <AT-ID>/
        workspace/             # 项目需要隔离写入时使用
        reports/<id>/          # 本机报告与选定证据快照
        <operation>/<request-id>/
          request.json
          result.json
          <tc-id>/              # 执行日志、附件和原生覆盖资料
```

定义保留原文、来源、ID 与版本。用例集保留稳定 TC ID、关联义务、源码引用、调试和设计评估。一次正式执行以任务、场景、用例、执行尝试及实际产品和用例版本定位。复审绑定对应执行与证据，修订写入新版本或新尝试。保存 Reviewer 原答，引用或索引可补录，原答保持原样。PLAN 是当前对话中的进度视图。恢复时，从已保存的业务产物、实际进程和当前授权重建待办。

区分场景义务覆盖与源码覆盖率。前者说明哪些业务检查有实际用例支持，后者使用项目原生工具的分母、命中和采集范围。报告单列零命中、未采集和工具不支持。

## 功能边界

「功能一致」按原版用户可获得的业务结果、权限边界、证据和停止点逐项验证。旧 Playbook 命令在清单中用于定位对照行为，新实现通过自然语言任务进入相应能力。原版的查看、手工执行、恢复、归档等能力也进入对照清单。任何暂缺项在候选版说明中列出，完整功能一致要等对应验收通过。 [原版固定提交](https://github.com/yangbobo2021/app-delivery-acceptance/tree/525e92f29fe5c625a37669f701897596d04edfd6)
